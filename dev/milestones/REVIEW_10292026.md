### 2c. Duplicated aliases after `clear = TRUE` resets (H03-1, H03-2)

Your 2026-10-28 answer changed `hydroloom_names(clear = TRUE)` so that it resets the registry to the vocabulary aliases plus `x`, instead of emptying it. The reset does not remove duplicates. When `x` repeats a vocabulary alias, the registry ends up holding that alias twice. Hydroloom_names H-01 found that a repeated alias makes later `hy()` calls warn `name_alias_duplicate`.

That has one consequence users will run into. The old way to restore a saved registry was `hydroloom_names(saved, clear = TRUE)`. Since `saved` already holds every vocabulary alias, this now lists all of them twice. After the change, a plain `hydroloom_names(clear = TRUE)` is the restore.

- **Option A:** the reset drops entries of `x` that repeat a vocabulary alias, so the old restore keeps working. This is an R change before M5, with NEWS.
- **Option B:** leave the reset as it is, and have the description state the new restore idiom, as the agent proposed.

Disposition: If clear = TRUE and x is not missing, I expect the current behavior. If x is missing, I expect it to revert to the default. i.e. the default value of x is the default that is set on package load.

### 2d. `flag_value_not_binary` can warn more than once per call (I23-2)

Every `.data.frame` method calls `hy()`, and internal steps may call `hy()` again on the same table. A flag column with a value such as 2 stays numeric through ingest, so one user call can raise the same `flag_value_not_binary` warning several times. Rule 1 asks that behavior changes stay few, which leans toward leaving it, but rule 1 is not a decision about this.

- **Option A:** leave it as recorded.
- **Option B:** warn once per user call. This is an R change, and it would need a way to tell an internal `hy()` call from the user's.

Disposition: Option B.
