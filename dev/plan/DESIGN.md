# hydroloom Python port — DESIGN

Why things are the way SPEC, VERIFICATION, and ROADMAP say they are. Each record is Decision, Why, Rejected. Where reasoning ran longer than a record holds, the decision log is cited by file and section (`init §13`, `refine-1 §3`, `refine-2`, `plan-refactor`). Drafted in bullets for a prose pass.

## 1. Principles and scope

- **Decision:** the Python package is the offline network-topology and indexing layer of the hydrofabric ecosystem, the role hydroloom plays in R relative to hydrogeofetch. A table of flowlines in, the same table with topology derived out. No HTTP, no gridded data.
  - Why: pynhd and HyRiver own web access; gdptools owns grid-to-polygon statistics. Keeping retrieval out is what lets both depend on this package instead of competing with it. The test for a function: if it needs a network connection it does not belong here. (init §1)
- **Decision:** share the cases, not the code. R and Python are two readings of one written definition: the algorithm descriptions, the vocabulary, the conformance cases. When the implementations disagree and the definition is silent, the definition is the bug.
  - Why: every project that shares tests across languages (JSON Schema Test Suite, Apache Arrow's `arrow-testing`, Zarr fixture stores, Prophet's CSVs) shares inputs and expected outputs in neutral formats with a thin harness per language. The descriptions add what those projects get from a written spec, and they are most of the hydrofabric standard's normative text, relocated rather than added. (init §4, §6)
  - Rejected: shared Rust kernels as the way to prevent divergence in v1 (§4 below); porting the R test suite.
- **Decision:** expectations are generated by the R package, never typed, and Python consumes them until parity on a function. Parity is documented, not promised: an absent function is listed absent.
- **Decision:** every shared artifact is language-neutral and exists in one copy; no derived form of a shared artifact is committed. One derived file is committed beside them, `docstrings.json`, generated from `man/` (§6); `man/` is itself the precedent for a committed generated file in an R package.
- **Decision:** the authorship split is a split between sessions, not people. One maintainer runs every agent. A description-side session, with `R/` open, writes each function's description, cases, and any R edit; a Python-side session, with `R/` closed, writes the Python from the description and the SPEC anchors it cites. Nothing written in one session is read by the other except through the shared artifacts under `inst/extdata/`. The exemplar slice (`as_hy`, `representation`, `_route`, `make_index_ids`, `IndexIds`, `csr.py`) comes first and is reviewed disproportionately, because it sets the pattern everything else copies. (chat-decisions 1.3, 1.10)
  - Why: a Python-side session that has read the R body writes a transliteration, with R's loop structure and R's names, and the geospatial-Python community does not recognize it. A session that has only the definition writes Python, and where the definition is silent the silence surfaces as a question instead of as copied behavior. The second reading is also what finds the gaps in a description, which is the suite's whole point.
  - Rejected: one session for all layers (the port reads as R). The September version of this decision put a person on each side and argued from the maintainer's time; the isolation is the reason that survives.
- **Decision:** the R-side and Python-side work are decoupled after M3: the unit of work is description, cases, R-generated expectations, Python function, with no R extraction step, so phase-2 descriptions can be written while the agent ports phase 1. (chat-decisions 1.3)
  - Why: with extraction deferred (§4), nothing on the R side has to change per function beyond the intended changes, and the only serialization left is that a description exists before its port starts.
  - Rejected: M3 complete before M5 starts, as the September plan had it; that put every phase-1 description on the critical path at once.
- **Decision:** capture current R behavior first and change in a named step, except where current behavior is an accident no user could have relied on (locale collation, unstable sort order, an undecided tie), which gets the intended rule directly with a NEWS entry (SPEC D-16).
  - Why: the test is whether a user's existing result could change in a way they would notice. Capturing an accident first only holds the port back. (refine-1 §3)
- **Decision:** tooling arrives with the first function that needs it, not with the skeleton (ROADMAP M4).
- **Decision:** the milestone order is chosen so each is useful if the next never happens. M1 to M3 improve the R package and the standard with no Python written. That is what makes the plan safe to start.
- **Decision:** no compiled code in the first port; a Rust graph core is the expected end state, taken once the walks exist in both languages against settled descriptions (§4).

## 2. Repository

- **Decision:** one repository. (init §7)
  - Why: a change to an algorithm, its description, its expectations, and both implementations lands as one reviewed pull request. Precedent: Arrow, xgboost, LightGBM, Prophet. The R-side mechanics are solved: `install_github` subdir, r-universe `packages.json`, r-lib actions `working-directory`. Tag prefixes route release workflows; path filters route CI.
  - Rejected: a second repository; splitting later stays possible with `git filter-repo` if the suite outgrows the two packages.
- **Decision:** one root, both packages interleaved: R unchanged at root, Python in the standard `src/hydroloom/` layout with `pyproject.toml` at root, pytest in `tests/python/`. (init §8, refine-1 §1, refine-2)
  - Why: a developer from either community opens the checkout and finds the layout their toolchain taught them. Moving the R package breaks every dev-install path and pkgdown link for existing users for a legibility gain a README paragraph supplies. `src/` is where R expects compiled code and hydroloom has none, so the toolchains do not contend for it in practice: `R CMD build` applies `.Rbuildignore`, `pkgload::load_all()` finds no C sources and skips compilation, `R CMD check` runs only `tests/*.R`. The one trace is a NOTE when check runs on the working directory rather than a tarball.
  - Rejected: sibling `r/` and `python/` directories as Arrow and xgboost use, for the reasons above; `python/hydroloom/` as a workaround for `src/`, once the working-tree behavior of `R CMD INSTALL .` was confirmed harmless.
- **Decision:** the sdist uses a positive `only-include` list and carries the conformance data.
  - Why: an exclude list drifts silently as R files are added. conda-forge builds from the sdist and runs pytest in its test section, the one place a clean install is exercised on all three platforms. (refine-1 §1)
- **Decision:** the vocabulary files reach the wheel by hatchling `force-include`, not by a copy in the Python tree.
  - Why: one copy, the same way the wheel is a build-time copy of every `.py` file. The cost is a reinstall after editing the JSON in a checkout, which the pixi `install` task does.
  - Rejected: `sysdata.rda` with a `data-raw/` step and a sync test on the R side; a copy hook. There is one file and both packages read it at runtime, so there is nothing to keep in sync. (refine-2)
- **Decision:** the conformance directory is Rbuildignored from the start; CRAN tests are minimal interface tests; R conformance runs from the checkout.
  - Why: CRAN's 5 MB ceiling applies to `inst/`, GeoPackage carries SQLite overhead before any rows, and designing fixtures for size rather than coverage is the wrong constraint on the artifact both implementations are read against. (refine-1 §3)

## 3. Dependency selection

- **Decision:** the runtime set is pynhd's minus its HTTP stack, plus scipy: pandas, numpy, scipy, shapely 2, geopandas, pyogrio. (init §1, plan-refactor)
  - Why, by package: pandas and numpy because every join-based algorithm is a frame operation in R and translates directly; shapely 2 because it is the same GEOS as sf and its vectorized API removed the per-geometry loop that made shapely 1 slow; geopandas because it is what every user in this community will hand the package, and pyproj comes with it; pyogrio because hydrofabric releases and the conformance suite ship as GeoPackage; scipy for the kd-tree, strongly connected components, and the triangular solve, and because it is numpy-only, ships wheels for every platform and Python in the matrix, touches none of the GDAL/PROJ/GEOS chain, and is already in HyRiver's stack through pygeoutils.
  - Rejected at runtime: networkx (pure Python, one object per node, does not scale to a CONUS network; offered as a conversion target behind `graph`); numba (trails new Python releases by months, colliding with the version matrix; a kernel written to run with and without it is written in numba's subset either way); pint (accepted by duck typing, never imported); pyarrow (GeoPackage throughout, so nothing needs it); xarray and rasterio (gridded data is gdptools' side of the boundary); the HyRiver retrieval layer (the dependency-level statement of scope).
- **Decision:** the version floor is the oldest version the code runs on, moved only when a required dependency drops it, never on the calendar. Python 3.10, pandas 2.2, shapely 2.0, geopandas 1.0. R Imports get floors the same way, found by testing. (refine-1 §3, refine-2)
  - Why: the pygeoapi stance. Production deployments on old Linux distributions are a valid target, and forcing upgrades by policy is the behavior this package avoids. Nothing in the plan needs pandas 3, since identifiers are coerced on ingest and the harness compares after coercion. The cost lands on how code is written, not on who can install it. SPEC 0 is named in the README as the policy not followed, so the reasoning is on record.
  - Rejected: upper bounds in `[project]`; the pixi lockfile pins the developer environment, and the scheduled `py-upstream` job is what notices when a new major breaks something.
- **Decision:** development dependencies, each with the job it does: hypothesis (the space between conformance cases, and the permutation-invariance property); import-linter (the kernel boundary held mechanically); pooch (one realistic-scale fixture the repository never carries); jsonschema (the definition both implementations are read against is itself checked); towncrier (fragments instead of the merge conflict that `CHANGELOG.md` is in a two-package repository); hatch-vcs (a release is a tag and nothing else); numpydoc; asv (every compiled-kernel decision is measured, so the instrument exists before the first one). (refine-1 §1)
  - Rejected: an action that opens issues on scheduled failures; a red job and the default email are enough at this scale.

## 4. Kernel boundary and the Rust end state

- **Decision:** all graph computation sits below one boundary in both languages, behind array-only interfaces; CSR is canonical; `IndexIds` is the one object that crosses. (init §13, §14)
  - Why: this is already hydroloom's pattern, an adjacency structure built with data.table and walked in base R over what is effectively a C structure. Naming the boundary lets a Python kernel be pure numpy today and compiled later without touching callers, and lets profiling and replacement happen per kernel. CSR is what scipy, igraph, and GraphBLAS consume; it has no sentinel, since a terminal is an empty range; R's padded matrix is the ELLPACK view of the same thing. Precedent: pyflwdir, pysheds.
  - Rejected: a graph library at the boundary; "the slow parts" as the boundary instead of all graph work.
- **Decision:** cross-language signature match (SPEC K-6) applies only to the named kernels: the compiled-kernel candidates below, `project_point_to_line`, and the Levenshtein kernel. Everything else below the boundary is language-local, held by the import-linter contract and per-kernel profiling, and the manifest marks it so. (chat-decisions 1.2)
  - Why: K-1 as first written sent every graph computation, vectorized walks included, through a kernel with a matched signature; under the authorship split that hands R's loop structure to the Python side, since only the description-side session can write those signatures into descriptions. pyflwdir, pysheds, and scipy's csgraph treat a kernel as the smallest unit that cannot be vectorized and leave the rest as numpy in the layer above. The named kernels are where tie rules run on numbers both languages must sort identically, which is the property the match protects.
  - Rejected: every kernel matched (the September rule).
- **Decision:** R kernel extraction is deferred, per kernel, to the moment a compiled-kernel decision fires for it, proven then by the conformance cases that have existed since M3; only the named kernels will ever be extracted. New R code written for the intended changes follows K-4 and K-6 as it is written; existing bodies are left alone. (chat-decisions 1.3)
  - Why: with the signature match narrowed, extraction's remaining consumers are the K-6 match on named kernels and the oracle role when a Rust core lands, both Rust-contingent, while its cost, a refactor of the expectation generator, is not. In phase 1 the only named kernel is the DFS under `navigate_network_dfs`. The cases that would prove an extraction preserved behavior are the same cases whether the extraction happens now or on the day a core is written, so nothing is lost by waiting.
  - Rejected: extraction in lockstep with the port (the September rule, refine-1 §3): value contingent on a Rust core that may never come, risk on the oracle now.
- **Decision:** a Rust graph core serving both packages is the expected end state, with two triggers, and the second is the one expected to fire: per-kernel performance when profiling shows a sequential loop is the bottleneck at scales users run; or consolidation of the whole graph layer, everything from `id`/`toid` columns to a walked graph, once the walks exist in both languages against settled descriptions. (init §14, refine-2)
  - Why: the graph code is where every rule with no tolerance lives (adjacency order, sibling order, sentinel, tie-breaking by identifier), and one core makes that class of divergence impossible rather than tested for. The sequence matters: the numpy and base-R kernels are written first because the second reading is what finds the gaps in a description, and because a Rust core written first is the implementation nobody else on the team reads. When the core lands, the numpy and base-R kernels stay as the conformance oracle, small and slow and unshipped, so the suite keeps its two-readings property.
  - Cost: the toolchain, not the crates. cargo on every source-install machine, per-platform wheels through maturin, CRAN's vendored-crate rules and build-from-source on every platform it checks, extendr keeping pace with R releases. A dependency-free Rust core carries nearly the whole cost of one with dependencies; petgraph versus a hand-rolled CSR is a choice for that day.
  - Layout on that day: `crates/hydroloom-core/` (pure Rust, no bindings), `crates/hydroloom-py/` (PyO3), `src/rust/` (extendr, where rextendr puts it), `src/Makevars`, `src/entrypoint.c`; `src/rust/vendor/` generated by `cargo vendor` at `R CMD build` for CRAN's no-network build; maturin pointed at the core by `manifest-path` and at the package by `python-source = "src"`. Nothing moves; `.Rbuildignore` narrows from `^src$` to `^src/hydroloom$`.
  - Boundary for the core: Arrow. One type built from Arrow `id`/`toid` columns (CSR both directions, the id map), one function per kernel taking that handle and attribute arrays. `IndexIds` and the R list become views over the handle, so a user holding a pre-built index keeps the same API. nanoarrow and pyarrow carry integer buffers zero-copy, as geoarrow-rs does, and the same boundary then serves DuckDB and polars without a change to the kernels.
- **Decision:** compiled-kernel candidates, if ever: level path assignment, Pfafstetter, many-start DFS, bridge detection (`get_bridge_flowlines`, a Tarjan-style walk that `accumulate_downstream` needs on non-dendritic networks; scipy has no bridges routine), and the attribute-guided modes of `navigate_hydro_network`. Not candidates: CSR construction (already C through pandas and data.table), frontier walks (vectorized), dendritic accumulation (a sparse triangular solve or a single sorted pass), cycle detection (scipy SCC), kd-tree search (compiled on both sides).
- **Decision:** no parallelism or progress reporting in v1; joblib above the boundary if ever. R's `future` and `pbapply` have no counterpart here yet. `fastmap` (R's hash map for the DFS) needs no analogue; a numpy array or dict does the job.

## 5. Build and environment

- **Decision:** pixi, with one manifest in `pyproject.toml`. (init §2)
  - Why: the weight of this stack is GDAL, GEOS, and PROJ, where conda-forge resolution matters; pixi resolves conda-forge first and PyPI second through uv. Tasks are the only entry points, so CI runs what a developer runs against the same lockfile. Two manifests is the failure mode the one-manifest rule exists to prevent.
  - Rejected: `pixi-build`, a preview feature aimed at compiled and mixed-language packages, which a noarch pure-Python wheel gains nothing from; a separate `pixi.toml`; the two pip-based CI jobs run outside the lockfile deliberately, because their point is to.
- **Decision:** hatchling as the build backend.
  - Why: reads the standard `[project]` table, so setuptools or flit could replace it; the wheel is built the ordinary PEP 517 way and the conda-forge feedstock consumes the sdist.
- **Glossary** for R developers (init §3):

| R | Python | Note |
| --- | --- | --- |
| `DESCRIPTION` | `pyproject.toml` `[project]` | `Imports:` ↔ `dependencies`; `Suggests:` ↔ `[project.optional-dependencies]` |
| `R CMD build`, one and unnamed | build backend in `[build-system]` | hatchling chosen |
| CRAN source tarball | sdist | |
| CRAN binary | wheel | a pure-Python package produces one `noarch` wheel for every platform, the analogue of an R package with no `src/` |
| CRAN binary builders | conda-forge feedstock | built from the PyPI sdist; one-time recipe from grayskull, bot PRs after |
| renv | pixi | developer-side only |
| `devtools::test()` | `pixi run test` | |

- **Decision:** the `r` and `docs` environments run on Linux only in CI; the Python matrix runs on all three platforms.
  - Why: R from conda-forge on Windows is less well exercised, and the docs build is the mixed-language case pixi is built for. (init §2)

## 6. Shared artifacts

- **Decision:** the vocabulary is one JSON file both packages read at runtime, replacing the mapping hard-coded in hydroloom's `hy` layer. (init §6, refine-1 §3, refine-2)
  - Why: the single highest-value shared artifact. Attribute names are what users see, and drift there is what they notice first. A type is the set of checks the harness applies to a column, so a value that needs a check no type can name is a missing type; that is how the eight types were found, `code` and `fraction` last, when `divergence` values and `divergence_fraction` sums had checks living only inside `check_hy_graph`. `tier` and `plain` exist for the reader: a forty-row definitions list becomes six core terms open and the rest collapsed, and `mainstem`, the one word a river scientist uses that no version of the package defined, gets a concept entry.
  - Rejected: per-source type overrides (the type policy is the point of the file; a source that disagrees is converted on ingest); grouping or hierarchy in the file (belongs in docs).
- **Decision:** GeoPackage for fixtures and expectations, read by sf and pyogrio. (refine-2)
  - Why: both are already dependencies, so the harness adds none. The format carries what the comparison needs: declared column types so a digit-string identifier stays TEXT; NULL distinct from the empty string, which the canonical `toid` fill depends on; row order by `fid`. Expected outputs are one file per function with a layer per case so SQLite's per-file overhead is paid per function.
  - Rejected: Parquet with `arrow` and `geoarrow` on the R side (a dependency the harness would add, and byte-identical Parquet across R arrow and pyarrow is fragile; comparison is by value and dtype after coercion regardless). testthat `_snaps/`, an R-specific format.
- **Decision:** the manifest inlines nothing: every input and expectation is a file, even for three-flowline cases.
  - Why: each harness then has one code path.
- **Decision:** algorithm descriptions have one fixed shape enforced by a validator, with Definition stated as a property of the output rather than as steps.
  - Why: the property is what hypothesis asserts and what a different algorithm could also satisfy. The Edge cases and Remedies sections exist because each boundary fixture is a place two implementations diverge by accident, and each forces a sentence into a description that is not there today. Remedies cite keys in the authored catalog (below), so the two packages say the same thing and the generated "when you see this error" page cannot drift. (refine-2)
- **Decision:** `requires` is declared in code, not read from the manifest at runtime: a registration decorator in Python (`@requires(...)`, filling a module-level registry that `capabilities()` and `_route` read), a hand-written table in R; the description's YAML front matter is the authored source, the manifest references it, and CI asserts both code tables equal it. (chat-decisions 1.1)
  - Why: the manifest and the descriptions are Rbuildignored and not force-included, so neither installed package can read them; S-1 forbids committing a derived form. The xarray-backend and scikit-learn-tags pattern puts the declaration beside the function it describes and lets the test, not the runtime, keep it honest.
  - Rejected: `capabilities()` generated from the manifest (unreadable at runtime); a committed derived table (S-1).
- **Decision:** remedies are an authored message catalog, `inst/extdata/remedies.json`, keyed by condition with `str.format` placeholders, the fifth shared artifact, shipped beside the vocabulary and read at the raise site by key; the gettext pattern. (chat-decisions 1.1)
  - Why: same runtime problem as above; and a catalog that is authored rather than derived can be edited without regenerating anything, which is what a message table is for.
  - Rejected: error text derived from the descriptions' Remedies tables at build time (a derived committed artifact, and one more generator).
- **Decision:** roxygen stays the authored documentation source; `docstrings.json` is generated from the committed `man/` by `tools::parse_Rd()` in a `dev/` script, committed, CI-diffed, and force-included; the Python decorator composes numpydoc docstrings from it at import. (chat-decisions 1.1, 1.5)
  - Why: the hydrology is written once, where the R maintainer already writes it. The roclet alternative existed to resolve inheritance, and the package has none to resolve (`@inheritParams`, `@template`, `@family` zero; `@inheritSection`, four uses as of 1.3.0, is resolved by roxygen into `man/`). The Rd tag inventory is small enough that a sixty-line walker covers it. Import-time composition has pandas `_shared_docs`, matplotlib `_docstring.Substitution`, and scipy `doccer` as precedent, and `numpydoc.validate` on the imported objects is how pandas validates the result.
  - Rejected: the description's Signature table as the documentation source (the September A-13; it made David write every argument twice); a roxygen roclet (unneeded); hand-written Python docstrings (two sources to drift).
- **Decision:** the suite is versioned independently of both packages.
  - Why: an R patch release should not imply a Python release, and a fixture change should be visible as a suite version change in both changelogs. (init §6)

## 7. Conventions: the reasoning behind the rules

- **Identifiers are two types in R, 32-bit integer or string, fixed on ingest by value; one type in Python, string.** (init §6, refine-1 §3, plan-refactor; amended 2026-10-25)
  - Why: this is where the two languages disagree most and where a wrong default passes most tests. pandas promotes an integer column with one missing value to float; a `toid` that silently becomes float passes value comparisons and fails an equality join. A dtype-based rule cannot be symmetric because sf reads a 64-bit column as double and R never sees an int64 to react to; a value-based rule gives the same identifier type from the same file in both languages, and identifiers that fit in 32 bits never need a 64-bit type on either side.
  - Why strings only in Python (2026-10-25, answers-2026-10-25 §1): the port is new development, and David's standing preference for new development is string identifiers. The value-based two-type rule bought the same dtype from the same file in both languages, at the cost of an int32 ingest path and a re-cast after every pandas reduction that widens to int64; one type removes both. Nothing in the hot path cares: kernels take dense positions and never identifier values (K-6), D-1 tie rules already compare identifiers as strings, and `IndexIds.uniques` is an Index of strings. R keeps two types because changing `hy()` would break existing users. The harness absorbs the difference in one place by comparing identifiers as text (S-7).
  - Rejected: nullable extension dtypes in the public API (a second missingness model pandas users would have to learn); bit64; `df.attrs` for original names (pandas drops it through `concat` and some merges, so a user's own frame operation could lose it). (refine-2)
- **Byte order, never locale, for every sort on identifiers.**
  - Why: the only collation both languages, every platform, and every database reach without configuration, and identifiers are opaque so no human-readable order is owed. In R the guarantee is a version floor on dplyr rather than a `method = "radix"` argument, since `arrange` followed the session locale before 1.1.0. (refine-2)
- **Sibling order in `sort_network` by identifier alone; adjacency lists in `make_index_ids` in identifier order.**
  - Why: today's R order is DFS visit order, which follows adjacency order, which follows input row order. The adjacency rule is the one that closes the path by which row order reaches a result; with it, permutation invariance is one hypothesis test that catches the widest class of defect at the lowest cost. A caller wanting mainstem-first order sorts on the columns it has, which is what `add_levelpaths` already does internally. (refine-2)
  - Rejected: levelpath-first sibling order, which would make `sort_network` depend on which columns happen to be present.
- **Output order of `sort_network` is compared exactly.**
  - Why: a sort whose order is unspecified is not useful to code that accumulates in that order; making it contract is what lets path length and arbolate sum be reproducible.
- **SCC always in `check_hy_graph`; `loop_check` removed.**
  - Why: the pairwise test and the gated DFS answer different questions and can disagree on a long cycle. Tarjan on a CSR is cheaper than the DFS it gated and finds everything the pairwise test finds, and the `reciprocal` label is what makes a row actionable, since a reciprocal pair is usually one flowline whose `toid` points the wrong way. (refine-2)
- **Tolerances anchored on meter-scale source precision, `rtol = 0`.**
  - Why: hydrographic coordinates are good to about a meter, so two results that agree to a meter are the same result and the harness should not resolve finer than the data. Every float hydroloom produces is accumulation, selection, measure arithmetic, or GEOS geometry, and the float error in all four sits ten or more orders of magnitude below a meter, so one rule covers them. Bit-reproducible accumulation across R's extended-precision `sum` and numpy's float64 is unachievable and unnecessary. `tie_tol` shares the anchor and is a constant, not an argument, until a real case calls for tuning. (refine-1 §1, refine-2)
- **Meters at the API boundary, exact CRS factor, geographic input raises.** (init §17)
  - Why: sf reports meters for geographic data under s2 and degrees under GEOS for the same input, a divergence the conformance suite cannot see; one unit removes the question. R's 0.01-degree default radius varies with latitude and is not a distance at all east–west, applied without telling the user. R warns for one minor release because it has users; Python raises from the start because it has none.
  - Rejected: converting feet by heuristic rather than the CRS's reported factor; requiring metres outright, which would reject valid state-plane data.
- **Bare numbers pass through; formal units optional, converted at the boundary; a warning only where a mislabeled unit produces a wrong number.**
  - Why: attribute arithmetic elsewhere combines values from one column or scales by a fraction and is correct under any consistent unit; only `navigate_hydro_network`'s `distance` is compared against a column. A warning on a correct call is the pandas behavior people mute, so it is confined to that one place. (refine-2)
- **Projection-based point indexing in place of nearest vertex.**
  - Why: nearest vertex is within `precision / 2` of the projection, so up to 5 m of offset at the 10 m default, and sf and shapely placing a densified vertex a float apart could move the answer. With projection on the original geometry, densification affects recall only. The kernel is written rather than delegated to GEOS `project` so the tie rule runs on numbers the kernel produced and the same code serves `make_attribute_topology` and `get_hydro_location`. (refine-2)
- **`string_score` is normalized Levenshtein with hydrolink's abbreviation table and selection defaults.**
  - Why: hydrolink's own difflib ratio has no R implementation and orders short names the same way; stop-word removal changes results users cannot predict, since "river" and "creek" appear inconsistently in source names. (refine-1 §3)
- **Functions, not classes; dispatch on the representation label, not the type.** (init §10 to §12, refine-2)
  - Why: "DataFrame in, DataFrame out" module-level functions are the scientific-Python idiom; classes are for state, and a cached graph is the one state, which `IndexIds` holds as a plain dataclass. R's `UseMethod` looks like type dispatch but the class it reads is a column-derived label refreshed by `classify_hy` on every entry, so copying the mechanism would copy the wrong axis. Subclassing DataFrame is the source of long-standing bugs in packages that tried, because most pandas operations return the base class. Deriving the pattern on each call costs a few column checks and means a user's own `merge` can never leave the table mislabeled. `capabilities()` and the representation map are generated from the decorator registry the functions declare, and CI checks the registry against the manifest's `requires`, so the three cannot disagree (§6).
  - Rejected, in order: `functools.singledispatch` as the primary mechanism (chosen first as the S3 analogue, dropped once the R class system was read directly and found to dispatch on a label, not a type); boundary conversion plus rare singledispatch; narwhals, `__geo_interface__`-style protocols, plum. A third party bringing a polars frame gets nothing from a registration point in front of a pandas body; what they get is the conformance suite and the descriptions, which are the actual contract.
- **The first argument is `network`, exempt from the identical-name rule.** (chat-decisions 1.7)
  - Why: A-16 mixed `df` and `x`, A-17 used `x`, R uses `x` throughout. The first argument is positional with `*` after it, so its keyword is almost never written and the cross-language benefit of matching it is near zero, while `network` says what the table is. Phase-3 functions take the noun they operate on (`points`, `lines`, `polygons`). Bodies use `net` or `network` so ruff `PD901` stays on.
  - Rejected: `x` for A-9 symmetry (says nothing); `df` (the pandas anti-idiom `PD901` exists to catch).
- **Three exception classes and no more.**
  - Why: fewer classes means fewer decisions at each raise site, which is where the maintenance cost lives. The rule for text is that an error saying what is wrong is the fallback and one saying what to do next is the target. (refine-1 §3)
- **No logging, no printed output, silent node-to-topo conversion.** (plan-refactor §5)
  - Why: the package's primary use is inside pipelines, where the caller owns the log and wraps each step with its own timing and context; a library that logs on its own adds lines the caller did not ask for in a format the caller did not choose. This is also the norm for the libraries this package sits beside: pandas, numpy, scipy, shapely, geopandas, and pyogrio emit nothing through `logging`; they use `warnings.warn` for conditions the caller should know about and otherwise return. The R package has nothing beyond `message()` behind `verbose`, so there is no R behavior to match. A message on a correct call is what pandas users mute.
  - If a function ever has something to say: the Python logging HOWTO's library convention and nothing more. One `logging.getLogger("hydroloom")` with a `NullHandler`, DEBUG level only, never configured by the package, so it is silent unless the caller opts in. That is the analogue of `message()` behind `verbose`, and it needs no API change to add later.
  - Rejected: INFO-level progress lines (gdptools and the HyRiver retrieval layer log, but they do network and raster work where progress is the point; a frame-in, frame-out function has no progress to report); a `verbose=` argument on every function; progress bars in v1.

## 8. Documentation

- **Decision:** one narrative, two code tabs: Quarto under the knitr engine with reticulate, `{.panel-tabset}` per step, built as pkgdown articles from `vignettes/articles/`. (init §4, §5)
  - Why: polars and DuckDB document this way and readers in this community recognize it. `vignettes/articles/` is built by pkgdown but not by `R CMD check`, so CRAN never needs a Python interpreter. API reference stays language-native (pkgdown; quartodoc under the same site) because that is what each community expects; quartodoc keeps one Quarto toolchain at the cost of intersphinx links.
- **Decision:** two new pages come first on the site. (refine-2)
  - The pipeline article, "From a file to a model-ready network": starts from New Hope as a GeoPackage on disk, a path rather than `system.file()`, because the reader has a file and not an installed package; one step per section (read, `as_hy`, `add_toids`, `sort_network`, `add_levelpaths`, `add_streamorder`, `add_pathlength`, write), each with the call in both tabs, one paragraph of hydrology on why a model needs the step (path length is how routing knows travel distance; stream order is what a parameter table is keyed on; level path is what "the main channel" means to code), and one line on what goes wrong if it is skipped; `capabilities()` printed after each step so the reader watches the table grow; closes by comparing against what hydrogeofetch would have fetched for the same COMIDs, and with a table of which columns a model reads (routing reads `pathlength_km` and `toid`, parameter tables `stream_order`, mainstem-aware output `levelpath`, area-weighted inputs `da_sqkm` and `total_da_sqkm`). It is the end-to-end test, so it cannot go stale without CI noticing.
  - The representation map: the four patterns as boxes, conversion functions as arrows, every analytic function under the box it needs, with a three-question key (is there a `toid`? are there `fromnode` and `tonode`? does `id` repeat?). Generated from the `_route` tables, so it cannot drift from the code, and it turns the guided error message from the tutorial it is today into the fallback it should be.
- **Decision:** the README and overview first screen are written for the person with a network file and a model to feed, not for a downstream maintainer.
  - What it says: a network as a table (one row per flowline, `id` and `toid`), what the reader's file probably calls those columns (`COMID`, `FromNode`/`ToNode`), what "prepared for a model" means, the three-row example, a link to the pipeline article. The audience statement moves one paragraph down and names the other route: hydrogeofetch and pynhd fetch NHDPlus and 3DHP ready to use and call hydroloom underneath; hydroloom itself is for a network that came from somewhere else. The S3 discussion that opens the overview today moves to the API-shape article.
- **Decision:** three orientation paragraphs, each placed where a reader meets the question. Catchments versus flowlines, on the overview's first screen (a flowline is the line of the river, a catchment the area draining to it; both carry the same `id`; the choice is what the model reads). Non-dendritic, at the top of that article (`is_dendritic()` says which yours is; a dendritic network can skip the rest). Which columns a model reads, as the pipeline article's closing table.
- **Decision:** argument meanings are written once, in roxygen, and reach the Python docstring through `docstrings.json` (§6, SPEC A-13); an argument taking a column name is documented by what the column has to mean, never by an example column from one dataset. The language-neutral phrasing pass happens per function in the same PR as its description. First fixes: `add_levelpaths` (`name_attribute`, `weight_attribute`, `override_factor`), `add_divergence` (`coastal_outlet_ids`, `inland_outlet_ids`), the `divergence` column `add_streamorder` consumes.

## 9. Releases and maintenance

- **Decision:** both packages are one USGS software product with one landing page and one USGS software DOI; no Zenodo. (init §17)
  - Why: the GitHub–Zenodo hook is not enabled, so prefixed tags create no records and there is no per-package concept DOI to reconcile. Tag prefixes are kept only to route build workflows.
- **Decision:** publisher of record is code.usgs.gov for R and Python alike; the GitLab release pipeline uploads with a project-scoped PyPI token. (refine-1 §2)
  - Why: releases come from the official repository. Trusted publishing covers GitHub Actions and gitlab.com but not a self-hosted GitLab, so the token is the mechanism; what is given up is PyPI's provenance attestation, nothing functional. Development CI stays on the GitHub mirror where pull requests happen. Mirror authority was never in question once current practice was read: development on GitHub, official builds on code.usgs.gov, by the README.
- **Decision:** the Python release is two-stage and mirrors the R package's current practice: a hand-pushed `rc/py-<version>` branch runs the full pipeline to TestPyPI; the `py-v<version>` tag on the same commit, created on GitHub after merge and pushed to code.usgs.gov by hand, runs the PyPI upload. The gate is phased: conformance in the release job from 0.0.1; scale and bench entries from the first tag after M6. (chat-decisions 1.8)
  - Why: the R package already releases this way (`rc/<version>` branch, registry tarball, manual CRAN, tag after acceptance); VERIFICATION §7's September row described a tag-triggered model the package does not use. hatch-vcs on an `rc/` branch yields a `.devN` version, which is the right thing to rehearse with. The token sequence (user-scoped for the stub, then project-scoped and revoke) follows from a project-scoped token not being creatable before the project exists.
  - Rejected: tag-only release (contradicts current practice; no rehearsal stage).
- **Decision:** the milestone pull request is the unit of merge; the review record lives in the tree at `dev/milestones/M<n>.md` with a disposition column only the maintainer writes; every agent commit carries an `Assisted-by: <tool>:<model-id>` git trailer and never `Signed-off-by` or `Co-Authored-By`; milestone PRs merge with a merge commit. The tree is authoritative over the GitHub thread. (milestone-workflow)
  - Why: with every agent on one machine and one branch, a pull request was only ever a diff plus a thread, and both exist locally; a per-function PR is a push cycle with no reader. The milestone file records the diff each reviewer judged, base SHA to head SHA, so a review is reproducible as `git diff <base>..<head>`, which is what makes it a record rather than a note; it is hashed with the code, survives a host move, and sits beside the planning documents. The trailer is the Linux kernel's form, adopted by Fedora, LLVM, and BOINC, and travels with every fork and the code.usgs.gov mirror. `Signed-off-by` is a legal certification only a person makes; `Co-Authored-By` names a human co-author. Squash would collapse the per-function commits and erase every trailer. The disposition column is the one place an agent is forbidden to write, by permission and by rule; that is the whole mechanism separating review from decision.
  - Rejected: a pull request per function (independence is enforced by Kiro permissions, not by the PR); transcript archiving (AGENTS.md rule 7: findings, not deliberation); git notes (do not travel by default).
- **Decision:** 0.x is provisional and may break in minor versions; 1.0 is the first reviewed release, defined by a milestone (parity with hydroloom 1.3.0, phases 1 to 3; 2026-10-25), not a date; `Development Status :: 4 - Beta` and the provisional disclaimer in the README until then, which also says that a pre-1.0 minor release may change or remove an interface without the A-11 warning cycle (2026-10-25). Releases are small and frequent so a merged function reaches PyPI within weeks rather than waiting on CRAN's cadence.
  - Why: USGS code is provisional and review happens only at major releases.
- **Decision:** a release is a tag and nothing else: hatch-vcs version, towncrier changelog, `only-include` sdist, `CITATION.cff`, PEP 639 license, `py.typed`, `register_names()` as a context manager so tests and threaded callers do not share mutable registry state, `FutureWarning` for deprecations because that is what pynhd and gdptools catch. (refine-1 §1)
- **Decision:** a co-maintainer from the gdptools side is named from the first commit. Deferred 2026-10-25: a person is identified but not formally involved; exemplar and named-kernel items are flagged in the Log for their review when they join, and nothing blocks on it (answers-2026-10-25 §4).
  - Why: the Python community files issues in its own idiom, and review cost is lower for someone fluent in pandas conventions. The cheapest mitigation available and not to be deferred. (init §6)
- **On overhead:** the fixed overhead of two packages (two release processes, two changelogs, a feedstock, two sets of bot PRs) is not removed by anything above. What the architecture removes is the variable overhead, divergence between implementations, which is the cost that compounds. Every convention in SPEC exists to convert an implicit behavior into an artifact both packages consume.
