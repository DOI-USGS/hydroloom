# hydroloom Python port — RULES

The maintainer's standing rules: the opinions behind the dispositions in `dev/milestones/`, written down once so an orchestrator applies them without asking. SPEC holds the rules of the package; this file holds the principles for deciding what SPEC and a description leave open, and for how the work is recorded. An agent that finds a principle here that decides its case applies it and cites the id. An agent that finds none takes the reversible call and proposes a line for this file in the run's `REVIEW_<date>.md`; the maintainer's answer there is how the file grows.

Each principle is stated as its spirit, then the cases already decided under it, so a new case is judged by the spirit and the decided cases show how far it reaches. Every line is the maintainer's. The first draft (2026-10-29) was assembled by an agent from the disposition text in `REVIEW_10272026.md`, `REVIEW_10282026.md`, `REVIEW_10292026.md`, and the status columns of `M1.md` to `M3.md`; the sources under each principle name the dispositions it was read from. Behavior principles are `B-<n>`; process principles are `P-<n>`.

## Behavior

### B-1. A function returns a correct answer or stops

A function never returns a plausible wrong answer. It raises only when it cannot form its documented output; when the problem can be part of the output, it returns the output. So a function that checks a network lists every problem it finds, a function that transforms a network raises on a problem it cannot resolve, and a function that reports what is possible answers rather than raises. A coding detail never silently cuts the network or turns a flowline into a terminal, because a cut network is a wrong answer the user cannot see. Running a name-aligning function on its own output never raises, except after a two-way tie: the losing alias then sits beside the name it lost, and the second pass raises `name_alias_conflict` as it would on the same input from the user. The `permanent_identifier` rule runs before the conflict check (2026-11-03, replacing that day's earlier sentence). A missing `id` value raises at ingest in Python, naming the rows by position (I-12), since no function can name a flowline it cannot identify; an agent drafts the catalog key for the M6 read (2026-11-03). A predicate answers for the function it predicts: `is_hy(x)` is true only where `as_hy(x)` returns without raising and changes no name or identifier type (2026-11-03).

Decided under it: `check_hy_graph` lists repeated (`id`, `toid`) pairs as their own table while every transforming function raises on them at ingest; `capabilities` answers on a table with no `id` while `representation` raises; a repeated pair is an error whether the rows are identical or differ elsewhere, and a fixture that carries one is the defect; a missing `tonode` makes a terminal that stays a target; a broken divergence coding raises; a second pass over a two-way alias tie raises; `is_hy` on a table with no `id` is false, since `as_hy` raises there.

From: REVIEW_10282026 rule 3 (D3-162, D3-166, D3-167), rule 4 (D3-158); D3-56, D3-57, D3-72, D3-74, D3-196, D3-209, D3-210, D3-215, D3-218; REVIEW_11022026 items 2 and 4; REVIEW_11032026 items 1 and 5.

### B-2. The user is told what they can act on, once

A problem is named by what the user can find: the row's `id`, never its position, unless the `id` value is itself the problem. A value the function does not read passes through untouched. A coding the function reads is accepted when it has one physical reading and refused when it has none or several. Where a coding is tolerated, the function warns, names the rows, and warns once per user call; the tolerance lives in Edge cases, is tested by asserting the warning rather than the output, and is never advertised as supported, since some users will want to treat it as an error. A-10 covers conditions a user can meet. A guard only a developer can trip, at import or in a test helper, raises a built-in exception carrying the identifier, with no catalog key (2026-11-02). A warning points at the user's call: its stack level is the first frame outside hydroloom, not a fixed number. An argument that names a column the table lacks raises `KeyError` carrying the column name, as pandas does, with no catalog key (2026-11-03).

Decided under it: no result carries a `row` column; a flag value other than 0, 1, or missing passes through with a warning; a 0 at a split is read as the main path with a warning; a lone downstream flowline coded 2 is connected to with a warning; a Postcondition that bound a tolerated coding was narrowed to the supported case; internal re-ingest does not repeat a warning; the docstring composer's import-time `KeyError("<alias>.<argument>")` carries no catalog key.

From: REVIEW_10282026 rule 3b (D3-160, D3-173), rule 4 (D3-152, D3-174, I2-3); REVIEW_10292026 1d (D3-182, D3-186, D3-193), 2d (D3-206); D3-54; REVIEW_11012026 item 4; REVIEW_11022026 items 5 and 7.

### B-3. The contract is what was intended, not what R happened to do

An R behavior no user could have relied on is an accident: it is fixed in R with a NEWS entry and never captured as a case, and the Python port matches the intent. A behavior a user could have relied on changes only as a named step: a ROADMAP §4 row, the R change with NEWS, regenerated expectations. Changes of that kind are acceptable in a minor release and kept few, and none lands without a disposition or a §4 row that names it. Either kind is fixed in a run only when its function is a unit the kickoff names; found elsewhere, it is a `BACKLOG.md` row under the milestone that owns the function, so a run's scope does not grow. A fix that changes no behavior, shown by every conformance case passing and no expectation layer changing, is made in the run whatever it touches, an R body included (2026-10-30).

Decided under it, as accidents: an internal error on zero rows; a `.x`/`.y` suffix; a mislabelled main path and a wrong edge count; a silent no-op on an uppercase alias; an evaluation-depth error; a network cut above a missing `tonode`; neighbor and sibling order following input row order; geometry reaching a `distinct()`. As named changes: upstream walks splitting at every terminal.

### B-4. One meaning, one name, one type

A quantity has one vocabulary term; a source field that carries that quantity is an alias of the term, added when the description that reads it lands, with a `values` map where the source codes differ. A function that recomputes a term replaces the column. A type is the meaning, not the source's coding: a flag is boolean and 1/0 is converted on ingest, and the harness compares the stored type. Every function aligns names before it reads them, Python through `as_hy` and R the same way (to confirm; REVIEW_10292026 1h). Where hydroloom has to choose a convention, it takes NHDPlus's: 0 for no neighbor in a sort-reference column, accumulation routed down the main channel unless a fraction apportions it, Strahler order with the divergence clause, measures 0 downstream and 100 upstream. One word per concept: "terminal" for a `toid` outside the table and "outlet" for the feature and the argument; a split is a divergence with a main and a minor channel; `navigate_network_dfs` directions are graph walks, not NLDI modes. I-9's ban on nullable dtypes covers computed integer attributes; a flag with a missing value is nullable `boolean`, since no other dtype keeps both its meaning and the missing value. An alias or a source tag may exist with no fixture that exercises it: the vocabulary supports fabrics no sample in hand represents (2026-11-03). The alias registry is process-wide, as in R. `with register_names(mapping):` restores the registry as it was on entry. A registered value that is not a hydroloom name stops, in R and Python, since an entry that can never rename a column is the silent no-op D3-65 fixed (B-3). A registered alias wins over a vocabulary alias for the same column, the alias of another term included. `hy_reverse(source=None)` restores the most recently registered alias for each name, lowercase as the registry holds it (D3-65). A function whose shared cases are all R-only joins `__all__` once it has a `generator: [python]` case (A-18). A function that types nothing is compared by value: its cases carry `compare: values`, and the Python harness brings the result to the layer's stored form instead of checking I-1 (2026-11-03). Where a description makes a language's answer depend on what that language has ported, the shared cases are R-only by design (`r_only:` with that description section), the function gets `generator: [python]` cases of its own on the same fixtures as the R cases, so the logic is checked on the same inputs in both languages, and it is exported on those; Python lists its registered functions in name order. A function whose every case is counted apart, with cases on both sides, reads `r, python` in the parity table (2026-11-04).

Decided under it: 3DHP `hydrosequence`, `dnhydrosequence`, `uphydrosequence` as aliases; eight more 3DHP fields to alias as their descriptions land; `add_topo_sort` replacing the input column; the flag conversion and the stored-type comparison; the no-neighbor value 0; the divergence-fraction fill of 1; the `hydrofabric` source tag kept with no fixture behind it; `align_names` compared by value, since it types nothing; `capabilities`, whose 14 shared cases carry `r_only: hy_capabilities.md §Algorithm`, whose Postcondition states Python's order as function-name order, and which joins `__all__` with its Python cases.

From: M1 H-04, H-07, H-09, H-10, H-12, H-14, M-07, M-09, M-18, M-28; hy H-12; REVIEW_10282026 decision 8; REVIEW_10292026 2b (D3-184), 1h (D3-197); D3-29, D3-69, D3-73, D3-76, D3-171, D3-188, D3-205, D3-210; REVIEW_11022026 items 1 and 6; REVIEW_11032026 items 4 and 6; REVIEW_11042026 item 2.

### B-5. Python is a new package

Python carries no compatibility debt. An R argument with nothing to do in Python is not in the Python signature. Where R warns for a release because it has users, Python raises from its first release. Python has one identifier type, string. The R package keeps its users' behavior and changes only under B-3.

Decided under it: `silent`, `include_conversions`, `long_form`, and `split` dropped; `no_id_column`, geographic input, and a repeated pair raise in Python while R warns or waits for its §4 row.

From: D3-17, D3-31, D3-47, D3-130, D3-147; DESIGN §7.

## Process

### P-1. A decision is made once

A disposition, a §4 row, a SPEC anchor, or a principle here settles its question. An agent that finds one applies it and cites it where the work lands, in the commit message, the Log entry, or the description's Changes line; it writes no Decisions row and asks nothing. A disposition is an instruction and wins over a description, the manifest, and existing R; a dispositioned row is not reopened. Where two dispositions disagree, the later wins and the earlier is noted as superseded. Where a description and SPEC disagree on something no code depends on, SPEC wins. A decided call that lands outside the run's units is a `BACKLOG.md` row under the milestone it blocks, read by the maintainer when that milestone starts. Only a case none of these decides, and that the run's units cannot land without, reaches the maintainer, as one item in the review file with the call taken and a proposed line for this file (2026-10-30). Where two binding sections of a frozen description disagree, the implementer follows Preconditions, and the review file decides which section is corrected under P-2 in the next description-side unit (2026-11-03). A case is `[r, python]` only when its `prepare` steps run in both harnesses; a disposition that marks a case whose `prepare` Python rejects waits for the `prepare` to agree (2026-11-03). A `via` that leads to a raise in the target function's Preconditions is dropped from the front matter. Preconditions say what the function accepts, and `via` says how to reach it (2026-11-03).

Decided under it: the `add_toids` `via: hy_topo: make_node_topology`, which `toid_already_present` stops, dropped from the front matter, the R `hy_capabilities` row, and the Python `@requires`.

From: REVIEW_10282026 rule 1; REVIEW_10292026 1f; the M3-close kickoffs; D3-161; REVIEW_11022026 item 3; REVIEW_11032026 item 3; REVIEW_11032026-run3 item 2.

### P-2. A change leaves nothing false behind

Whatever a change makes wrong is corrected in the same commit: roxygen, a description sentence, a manifest comment, a fixture-index entry, a plan document, a Log cell. Wording that was already stale before the run is one sweep at the end of the run, not an edit per unit. Log cells are filled by the agent by mapping: an applied finding `accept`, a reported row `accept`, a cell settled by a row `see D3-nn`, by a principle its id, a `verify` row `record`; `—` stays only where the review file carries the item. The R package is not restyled by a hook: styler and lintr stay out of pre-commit and CI until the maintainer restyles the package in its own commit, and Python, all new code, is formatted by ruff (2026-11-02).

Decided under it: the roxygen run 2 made false was fixed rather than queued; SPEC S-7 and S-4 were edited in the run whose harness change made them wrong; the twenty fixture-index entries and six manifest comments went in one housekeeping commit; a size estimate a harness outgrows is corrected in the plan, not met by cutting the harness (VERIFICATION §2 said a hundred lines; both harnesses were near 660 at M4).

### P-3. The suite tests what the description promises and nothing else

A bound value has a case that compares it; a bound order is `order: exact`; a Postcondition no case compares is given a case or moved to Edge cases. Every D rule a description cites has a fixture tagged with it, and a gap is closed in the milestone. The other direction holds too: an expectation layer stores only what the function writes, attributes only, the columns the function writes on real-network layers, geometry only where a case checks pass-through, every file under 1 MiB, and write mode deletes layers no case owns, so a regeneration never adds binary to history for columns nobody compares. A function whose input is process state rather than a table is tested in each language's own suite against its description, and joins `__all__` when both suites cover every Postcondition; it needs no manifest case. Its parity row reads `r, python` when every manifest case it has is R-only by design and the Log entry that exports it names the Python tests covering each Postcondition (2026-11-03).

Decided under it: `register_names`, whose mapping no manifest `args` literal can carry, tested in testthat and pytest; `hydroloom_names_unnamed_input` R-only by design, since Python's `register_names` takes a mapping and has no unnamed form.

### P-4. The maintainer's attention goes to the words only he can write, when they matter

Prose a user reads is the maintainer's: `plain` and `definition` fields, roxygen beyond correctness, `remedies.json` messages, README, articles, and a citation only he can supply. A milestone's Summary is drafted by the orchestrator when the done-check passes, marked `DRAFT:`, and edited by the maintainer (2026-10-30). An agent lists the sentence and the proposed fix once, in the review file, and does not edit it. Message text is reviewed in the milestone where R starts reading the catalog, not before; agents draft the keys a new raise needs for that read, and nothing types error text at a raise site. A finding with no anchor is recorded in the Log as `record` and goes nowhere else. A reader round is run when a description's binding sections change, because those are the implementer's contract; one round, one fix round that applies blockers and description-edit `should` findings, the rest under P-2. The round is per function and the reader reads the diff: the binding sections changed since the SHA of the description's last logged read, the whole file only the first time, and the Log entry records the SHA read. After its first round and fix round a description is frozen: it changes only from an implementer finding or a conformance failure, and a later reader finding on it is `record` (2026-10-30; M3 read all fifteen descriptions five times). Roxygen prose a user reads in R reaches the Python docstring in full, every `\section` under Notes. The only drops are the ones A-13 names: `Required attributes:` lines, `Required columns` sections, required-column lists and examples (2026-11-02). Where reused roxygen would be false in Python, the fix is in the roxygen: the description PR makes the shared sentences language-neutral and puts the R-only facts in sentences of their own that the substitution table drops (A-13). No Python-side table of replacement sentences is written; where a description's Definition already says it, that paragraph is the text (2026-11-03; the M5 exemplar's `PER_FUNCTION` entries are the case that decided it). A fact true only in Python is a roxygen sentence of its own beginning "In Python,"; R help shows it and the composer keeps it. Wording in shared roxygen that an agent drafted joins the Any time roxygen row. Roxygen marks an R-only fact with a sentence or paragraph beginning "In R,", and the R source of a Python docstring is its last Notes line. A substitution pair replaces a phrase with a phrase; a sentence is roxygen, however many fields it reaches, and lives there once (2026-11-03).

### P-5. A run is its kickoff

A run's units are the ones its kickoff file names, in that order, and the run ends on the last of them. A unit whose input cannot be obtained is skipped, with nothing committed and its BACKLOG row kept, and the run continues with the next unit that does not depend on it (2026-11-03). A run never adds a unit: what it finds goes to a bin (orchestrator.md). The kickoff is a committed file the orchestrator writes from `.kiro/context/kickoff-template.md` and commits before the run starts, so the run is reproducible from the record and the standing rules never live in a prompt. It is written when the maintainer says to continue and the last review file's Disposition lines are filled, from those dispositions and the open BACKLOG rows; the maintainer's message is the whole instruction, and he edits a kickoff only to disagree with it. A list of what the kickoff would hold is not an answer to that message; the committed kickoff is (2026-11-03). A function is `r, python` in the parity table when every case not R-only by design passes in Python; an R-only-by-design case carries `r_only:` with the anchor that makes it so, and the table counts it apart (2026-11-03). A `supported_by: [python]` case is Python-only by design (B-5) and counts apart in the parity table, as an `r_only` case does; it does not change the function's `supported_by`. It needs no anchor field, since B-5 is the anchor for all of them. A case whose reason is anything other than a B-5 raise is written `[r, python]` with the R side closed under B-3, not left `[python]` (2026-11-04). The exemplar slice (M5 run 1) lands before any phase-2 description is written, because it is the first test of a description as a contract an implementer reads blind; until then the two sides of the port are not independent. The orchestrator does the run work the plan assigns to the maintainer, apart from prose only he can write (P-4) and decisions in the review file. It builds nothing itself. Python under `src/hydroloom/` and `tests/python/` goes to `hl-implementer`. Everything else goes to `general-task-execution`, reviewed by `hl-style-reviewer` on the unit's diff (2026-11-01). Where a milestone's Deliverable and its Done-when disagree, the Deliverable wins. The Done-when item moves to the milestone the Deliverable names, in a `plan:` commit (2026-11-02).

Decided under it: M3's five close-out runs, each of which found its next unit in a done-check read; M4 run 1, whose kickoff the orchestrator wrote; the M4 PyPI stub, moved to M5; M5 run 1 unit 1, the hydrofabric fixture, skipped for no sample while units 2 to 4 landed.
